# 2026-11-06

**요약**: 대학 AX 캡스톤에서 우리 과제(대회 공고 hwp → 관리 화면 자동 입력)를 맡은 4팀을 멘토링하고 평가했다. 결과물 발표 날 우리 과제에서 2팀이 본선에 올랐고, 그중 디자이너 출신 학생의 1인 팀이 기업 8곳·약 40팀 가운데 우승했다. 가장 크게 남은 건 평가 기준이었다. 정합성을 "파일을 잘 읽었나"와 "가이드라인대로 냈나" 두 단계로 나누고 나서야 팀 간 차이가 보였다. 지어냄을 막는 마지막 관문도 AI 점검이 아니라 근거 문장을 원문과 기계적으로 대조하는 검사였다.

## 배경과 제약

회사가 대학의 AX 전환 사업에 과제 기업으로 선정됐다. 과제 설명 발표 뒤 과제 환경을 하루 만에 만들어 학생 5명(4팀)에게 줬다(→ 2026-11-01 일지). 학생들은 각자 받은 Claude API 키로 1단계(공고 → 대회 생성 폼)와 2단계(체급표 → 우리 체급 목록 연결)를 구현했다. 제출 마감은 금요일이었고, 그 전에 팀마다 2시간씩 멘토링을 했다. 두 팀은 사무실에서, 두 팀은 온라인으로 했다.

## 멘토링에서 다룬 것

모든 팀에 공통으로 다룬 건 세 가지다. 1차 추출 결과를 실제 화면에 넣어 보기, 공고에 없는 값과 정해지지 않은 칸을 다루는 가이드라인, 도메인 지식(어떤 설정이 어떤 역할을 하는지, 체급표를 읽는 기초)이다. 가이드라인을 가장 강조했다. 누가 써도 결과가 이상하게 튀지 않으려면, 채울 수 없는 칸을 비워 두는 기준이 있어야 한다.

팀마다 출발점이 달랐다. 한 팀은 프로젝트 세팅부터 같이 했다. 한 팀은 이미 동작하는 결과를 가져와 피드백만 했다. 한 팀은 Claude 가 hwp 를 잘 못 읽어서, 가장 잘 읽는 마크다운으로 바꿔 넘기고 모델별로 결과를 비교해 고르는 데까지 같이 봤다. 마지막 팀은 AI 가 참고한 원문 위치를 hwp 파일에 메모로 남기는 결과물을 냈다.

## 평가 기준 — 처음 생각과 달랐던 것

처음에는 학생이 올린 결과를 운영 데이터와 대조하면 정합성을 볼 수 있다고 생각했다. 하지만 전부 일일이 볼 수는 없었다. 또 공고만 보고 맞게 채울 수 있는 값과 애초에 없는 값이 섞여 있었다. 그래서 "공고에 있는 값을 맞게 넣었나, 없는 값을 지어내지 않았나"를 기준으로 잡았다.

이 기준으로 판정 화면을 만들었다. 학생마다 구현 방식이 달라도 같은 잣대로 보려고, main 위에 순수 추가로만 얹었다. 공통 파일을 하나도 고치지 않아 학생 브랜치와 병합 충돌이 0이 되게 했다. 판정은 칸마다 일치·비워서 맞음·비움·틀림·지어냄 다섯 가지다. 그 밖에 운영자 설정 칸을 건드렸는지, 체급 연결의 일치·누락·초과, 같은 공고를 다시 넣었을 때 결과가 같은지도 봤다.

| 축 | 배점 | 보는 것 |
|---|---|---|
| 정합성 | 40 | 있는 값을 맞게, 없는 값은 비움 |
| 가이드라인·재현성 | 20 | 운영자 설정·자동 저장·체급 자동 생성 없음, 같은 공고 두 번이면 같은 결과 |
| 실사용성 | 20 | 확인 필요 표시, 근거, 실행 조건 |
| 편의성 | 10 | 진행 표시·안내·오류 처리 |
| 설명 | 10 | 왜 그렇게 만들었는지 본인이 설명하나 |

데모는 블라인드로 공고 2개를 쓰고, 그중 하나는 두 번 돌리기로 했다. "원래는 되는데"는 0점이다.

발표 직전에 학생 서버를 로컬에 띄워 API 로 직접 돌려 보니, 판정 화면이 보는 건 절반뿐이었다. 정합성은 두 단계다. **1. hwp 파일을 제대로 읽었나. 2. 읽은 걸로 가이드라인대로 냈나.** 화면은 2번만 본다. 1번은 질문으로 채워야 했다. hwp 5.0·hwpx·hwp 3.x 중 어디까지 지원하나, 형식은 확장자로 판별하나 파일 앞 바이트로 판별하나, 세로로 합쳐진 표 칸은 어떻게 다루나, 깨진 파일을 올리면 어떻게 되나 같은 것들이다. 그 과정에서 내 착각도 하나 고쳤다. hwpx 를 옛 형식으로 알고 있었는데 실제로는 더 새 형식(zip+XML, 국가표준)이었다. 흔히 쓰는 hwp 라이브러리는 hwp 5.0 만 읽는다.

## 팀별로 갈린 지점

| | 팀 A (본선·우승) | 팀 B (본선) | 팀 C | 팀 D |
|---|---|---|---|---|
| 파일 읽기 | 라이브러리로 본문을 구조째 뽑음. 표는 `\| 칸 \|` 행으로, 글상자·그림 포함. hwpx 는 직접 파싱, 형식은 파일 앞 바이트로 판별 | 별도 엔진에서 직접 파싱. PDF·문서 파일·이미지도 받음 | 규칙 파서. 합쳐진 칸은 칸 개수로 채움 | 원문 위치를 메모로 남김 |
| AI 사용 | 큰 모델 2~3회(추출 + 점검) | 중간 모델 1회 | 없음 | — |
| 같은 공고 결과 | 30칸 모두 일치, 19초 | 30칸 중 29칸 일치, 11초 | — | 제출 없음 |
| 눈에 띈 것 | 검증 루프 | 원문 미리보기·문서별 대화·버전 관리·배포까지 갖춘 제품 수준 | AI 없이 동작 | 근거 추적 |

팀 A 의 검증은 AI 가 AI 를 검증하는 구조가 아니었다. 최종 관문은 기계적 검사였다.

```pseudo
요강 채우기(파일):
  문서 = 구조째 뽑기(파일)
  # 소개글은 원문 덩어리 번호만, 체급은 목록 안의 이름만 고르게 한다
  후보 = 추출 AI(문서)
  반복 최대 2회:
      # 근거 구절이 원문에 있는가, 금액·날짜가 근거에 보이는가, 요일·날짜 순서
      문제 = 규칙 점검(후보, 문서)
      if 문제 없음: 끝
      제안 = 점검 AI(문서, 후보, 문제)
      # ← 결정 지점: 고친 값도 규칙을 다시 통과해야 반영
      후보 = 규칙 통과한 제안만 반영(후보, 제안)
  # 돈·날짜 칸은 맞아도 확인 필요
  남은 칸 → 사람 확인
```

이 구조의 한계도 같은 곳에서 나온다. 근거가 원문에 있기만 하면 통과하므로, 원문에 있는 다른 날짜(계체일 같은)를 골라 와도 규칙은 잡지 못한다.

## 결과와 대가

- 결과물 발표 날 우리 과제 2팀이 본선에 올랐다. 그중 팀 A(디자이너 출신 학생의 1인 팀)가 기업 8곳·약 40팀 가운데 우승했다(전체 수상 4명). 기능 범위는 팀 B 가 훨씬 넓었다(바뀐 파일 860여 개 대 26개). 하지만 우승은 과제 범위 안에서 가이드라인을 지키고 검증 구조를 만든 쪽이었다.
- 같은 날 회사도 요강 AI 기능을 머지했다. 비교해 보니 설계가 많이 겹쳤다. 근거 문장 원문 대조, 요일·날짜 순서 검사, "같은 입력이면 같은 결과" 목표, hwp → PDF 변환과 변환 프로세스 제한이 같았다. 학생 코드를 참고한 흔적은 없었다. 같은 요구사항 문서가 공통 출처다.
- 다른 점이 오히려 배울 거리였다. 회사 쪽은 라이브러리가 주는 평문만 써서 표 구조를 잃는다. 체급표를 다루게 되면 표를 행 단위로 직렬화하는 학생 방식을 가져올 만하다. 반대로 운영에서 겪은 hwp 라이브러리 무한 루프(손상된 필드) 대비는 학생 코드에 없었다.
- 어긋난 곳도 하나 찾았다. 학생에게는 "운영자 설정 칸은 채우지 말라"고 했는데, 회사 기능은 안내문을 붙이고 채우는 쪽을 택했다. 평가 기준과 제품 결정이 다른 지점이다.
- 대가: 판정 화면은 로컬에만 있고, 학생 브랜치 전체에 일괄로 돌리지는 못했다. 발표 당일에는 학생 서버를 하나씩 띄워 정답 예시와 직접 대조했다.
