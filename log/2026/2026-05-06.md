# 2026-05-06

**요약**: 상장 출력용 HWP 템플릿 하나가 외부 라이브러리를 무한루프에 빠뜨려 운영 서버 스레드가 고갈되고 CPU가 치솟았다. 재기동으로 급한 불을 끄고, 격리 스레드 풀 1개 + 30초 타임아웃 + 사전 검증 + 슬랙 경보로 막았다. 핫픽스 두 번, 당일 머지.

## 배경과 제약
서비스 초기라 모니터링이 제대로 없었다. 운영은 가상머신 한 대에 jar를 띄운 구조. 상장 출력은 HWP 템플릿의 필드를 채워 파일로 내려주는 기능인데, 파싱·치환을 오픈소스 HWP 라이브러리에 맡기고 있었다.

## 막혔던 것
처음 본 건 에러 로그였다. 특정 템플릿 파일을 넣었더니 에러 로그가 엄청나게 쏟아졌다. 그 시점엔 "그 파일이 이상하다" 정도로만 봤다. 원인을 찾던 중에 서비스 지표가 이상했다. 스레드가 고갈되고 CPU 사용률이 뛰어 있었다. 에러가 많이 나는 것과 CPU가 뛰는 건 다른 얘기다. 에러는 던지고 끝나야 하는데 CPU를 계속 먹는다는 건 뭔가가 끝나지 않고 돌고 있다는 뜻이었다. 그제야 스레드가 무한루프에 들어가 있다는 걸 깨닫고 서비스를 내렸다 올렸다.

개발 서버에서 같은 파일로 재현했다. 라이브러리가 손상된 ClickHere 필드 컨트롤이 있는 HWP에서 필드 시작 위치를 찾는 루프를 못 빠져나왔고, 인터럽트도 무시했다. 즉 타임아웃을 걸어 요청 스레드를 돌려보내도 워커 스레드는 계속 돈다.

## 선택
15시대 1차 핫픽스는 타임아웃이었다. 요청 스레드만이라도 살리자는 것. 17시대 2차에서 구조를 바꿨다.

```pseudo
상장 출력(템플릿, 값들):
  # 라이브러리에 넘기기 전에 손상 패턴을 먼저 거른다 — 들어가면 못 빠져나오니 입구에서 막는다
  필드 구조 검증(템플릿)
  if 손상이면: 즉시 에러 응답
  # 격리 풀(스레드 1개)에 넘기고 30초만 기다린다
  결과 = 격리풀.제출(라이브러리.채우기(템플릿, 값들)).대기(30초)
  if 시간 초과:
      # ← 워커는 아직 돌고 있을 수 있다(인터럽트 무시). 요청 스레드만 살리고 사람에게 알린다
      슬랙 경보
      에러 응답 "비정상 상태 감지"
```

- 격리 풀을 2개가 아니라 **1개**로 했다. 무한루프가 또 나면 코어 하나만 먹게 가두는 것이다. 사전 검증이 대부분을 입구에서 걸러 주니 격리 풀에 작업이 몰릴 일은 드물다고 봤다.
- 타임아웃 에러는 일반 에러와 달리 "CPU 누수가 진행 중"이라는 시스템 신호라서, 예외 핸들러에서 이 코드만 따로 슬랙으로 보낸다.
- 에러 메시지도 "처리 시간 초과, 템플릿을 확인하세요"에서 "비정상 상태가 감지되어 차단, 관리자에게 문의"로 바꿨다. 사용자가 다시 시도하게 만들면 안 되는 상황이라서.

## 결과와 대가
- 재현 파일로 검증 통과, 당일 저녁 머지·배포.
- 대가: 상장 출력이 한 번에 한 건씩만 처리된다. 운영상 상장은 대회 끝나고 몰아서 뽑는 거라 체감은 없었다.
- 외부 라이브러리 안의 버그는 고칠 수 없다. 할 수 있는 건 격리·타임아웃·사전 검증·경보 네 겹이고, 이 사건이 "로그만 보지 말고 지표를 봐야 한다"는 걸 몸으로 알게 했다. 관측성 스택을 세우자는 얘기가 이 뒤에 나왔다.
