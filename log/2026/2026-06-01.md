# 2026-06-01

**요약**: 3월에 만든 외부 식별자 테이블 위에 외부 연맹 연동을 올렸다. sync(외부→우리 DB)와 link(사용자가 연결)를 용어부터 갈랐고, "팀 그룹 식별자는 저장해도 된다"는 직전 결정이 운영 데이터로 반증돼 컬럼을 지웠다.

## 배경과 제약
외부 연맹의 선수·지도자·팀 데이터가 별도 동기화 프로젝트를 통해 우리 DB의 미러 테이블로 들어온다. 사용자(지도자)는 회원가입이나 팀 관리에서 자기 외부 코드를 입력해 우리 엔티티와 연결한다. 우리 엔티티 1건이 외부 식별자 N건을 가질 수 있어야 하고, 사용자가 입력하는 비즈니스 코드와 동기화용 원천 PK는 섞이면 안 된다.

## 선택
- **용어 분리.** sync는 외부→우리 DB 단방향 가져오기(동기화 프로젝트 책임), link는 사용자가 우리 엔티티에 연결(API 책임). 같은 "연동"이라는 말을 쓰다가 책임선이 흐려져서 단어부터 갈랐다.
- **팀 코드 1개 입력 → 같은 그룹 전체를 N건으로 펼침.** 외부 연맹은 한 학교 안에 초·중·고 같은 그룹 단위 코드가 있고, 그 위에 학교 단위 식별자가 있다. 사용자는 코드 하나만 넣고 시스템이 같은 학교 그룹의 코드를 전부 찾아 식별자 N건을 만든다.
- **한 외부 팀은 우리 팀 하나만 점유.** 검색 단계와 저장 단계 양쪽에서 막는다.
- **외부 미러 테이블은 DELETE 금지.** 외부 사정으로 사용자 연동이 끊기면 안 된다.
- 식별자의 `code`는 내부 매칭 키, `metadata`는 표시용 스냅샷. 매칭 키는 휘발하면 안 되지만 표시용은 스냅샷이어도 된다.

## 막혔던 것 — 틀렸던 결정 하나
직전에 "학교 단위 식별자를 팀 테이블 컬럼으로 저장하고 생활체육 그룹 매칭의 게이트로 쓴다"고 정했었다. 운영 데이터를 점검하다 이상한 게 보였다. 정상 값 그룹이 1,832팀, `-1` 그룹이 439팀인데 `-1` 쪽에 실제 활성 학교가 몰려 있었다. 동기화 쪽을 뒤져 보니 이 식별자는 외부 연맹이 데이터를 갱신할 때마다 재할당되는 값이었다. 저장한 스냅샷은 다음 동기화 뒤에 stale이 된다. 그걸로 차단 검증을 하면 엉뚱한 팀을 막거나 통과시킨다.

선택지는 저장 유지(탈락), 저장하되 동기화 뒤 일괄 재계산(재계산 잡 비용 + 일관성 창), 저장하지 않고 매번 현재 연도 식별자 코드들로 미러 테이블을 1회 IN 조회. 세 번째로 갔다. 컬럼·필드·갱신 후처리를 다 걷어냈다. 트랜잭션당 조회 1회가 비용인데 인덱스로 충분했다.

## 결과와 대가
- 추상 외부 식별자 + 구체 3종, 미러 엔티티 5쌍, 사용자/관리자 측 서비스·DTO·Repository는 거울 구조로 분리(의도된 차이 3가지를 문서화).
- 지도자 자격 검증(이름+생년 대조)은 명세가 확정되지 않아 네 곳을 주석 처리하고 본체는 남겼다. 외부 정책이 바뀌면 본체 제거 전에 복원 경로가 있어야 한다.
- 교훈: 외부 시스템의 식별자는 "PK처럼 생겼다"고 PK가 아니다. 저장하기 전에 그 값이 시간에 따라 바뀌는지 운영 데이터로 먼저 본다.
