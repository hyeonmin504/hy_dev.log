# 2026-10-12

**요약**: 메일 포워더(SES 수신 → Lambda → 개인 메일로 재발송)를 도메인 하나에서 여러 도메인으로 넓히고, 다른 업체에서 산 새 도메인을 Route53으로 위임해 메일 주소 6개를 개통했다. 코드는 이전 설정 형식도 읽게 만들어 무중단으로 넘겼고, 막힌 곳은 코드가 아니라 DNS 캐시·IAM 조건·Gmail 지연 같은 바깥쪽이었다.

## 선택
설정 파일에 도메인별 블록(`domains: {도메인: {발신주소, 주소맵}}`)을 두는 쪽으로 갔다. 함수 배포와 설정 교체는 동시에 일어날 수 없어서, 새 코드가 이전 형식(최상위에 도메인 하나)도 그대로 읽게 했다. 순서는 코드 배포 → 기존 메일 테스트 → 설정 교체 → 기존 메일 다시 테스트. 수신 레코드(MX)는 맨 마지막에 넣어, 그 전까지는 새 도메인으로 메일이 아예 들어오지 않게 했다.

## 막혔던 것
- **도메인 위임.** 도메인은 홈페이지 빌더에서 결제한 거라 네임서버를 관리 화면에서 못 바꿨다. 채팅 상담으로 요청해 당일 바뀌었다. 삭제 후 재등록도 떠올렸지만, 공개되는 순간 남이 가져갈 수 있어 접었다.
- **사무실에서만 예전 사이트.** 구글 DNS는 새 값을 주는데 사무실 회선 DNS는 예전 네임서버를 약 15시간 더 기억하고 있었다. 모바일에선 열렸다. 레코드 TTL이 아니라 위임(NS) 캐시가 남은 것이다.
- **권한이 이미 있는 줄 알았다 — 틀렸던 가설.** 정책에 `ses:SendRawEmail` + `Resource: "*"` 문장이 있어서 새 도메인도 될 줄 알았다. 그 문장엔 `aws:SourceAccount` 조건이 붙어 있었다. 이 키는 서비스가 대신 호출할 때만 채워진다. 함수가 직접 부르면 조건이 맞지 않아 효력이 없었고, 시뮬레이터 결과도 implicitDeny였다. 실제로 권한을 주던 건 도메인 하나만 적힌 아래 문장이었다.
- **7명 그룹 메일만 안 왔다.** 1명짜리 주소는 바로 오는데 7명 그룹은 반송 0인 채로 15분 뒤에 들어왔다. 발송 메트릭의 Delivery가 1~2분 늦게 찍히는 걸 모르고 "배달 실패"와 "늦게 집계"를 한 번씩 잘못 말했다. 메트릭은 몇 분 뒤 다시 보고 판단해야 했다.
- **자동 배포인 줄 알았다.** 워크플로는 린트·테스트뿐이었고, 트리거 브랜치 이름도 실제 기본 브랜치와 달랐다. 이번엔 콘솔로 zip을 올리고 함수의 코드 해시를 로컬 zip 해시와 대조해 "머지된 코드 = 배포된 코드"를 확인했다.
