# 2026-05-08

**요약**: 엔지니어링 위키를 git 레포에 3계층으로 세우고, PR 머지를 트리거로 LLM이 위키를 점진 갱신하는 스킬을 붙였다. 자동 저장 대신 "충돌·차이·미확정만 컨펌"을 강제한 게 핵심 결정.

## 배경과 제약
코드베이스가 커지면서 LLM에게 새 요구사항을 던지면 도메인 패턴과 과거 결정을 몰라 일관성 없는 코드가 나왔다. 사람이 쓰는 위키는 정체돼 있었고, PR 본문은 그 PR 안에서만 살아 있어 검색도 교차참조도 안 됐다. 지식이 어딘가에는 있는데 LLM이 읽을 수 있는 자리에 없었다.

## 선택
| 선택지 | 결과 | 이유 |
|---|---|---|
| 수동 위키 유지 | 탈락 | 이미 정체 중 |
| PR 본문에 쌓기 | 탈락 | 검색·교차참조가 안 됨 |
| 외부 SaaS 위키 + 자동화 | 탈락 | LLM 컨텍스트 주입이 어렵고 권한·요금 |
| git 레포 위키 + PR 트리거 LLM 스킬 | **채택** | LLM이 직접 읽고 여러 파일을 비교·통합할 수 있다 |

구조는 3계층. ① 서비스 본체(사용자별 기능 설명) ② 엔지니어링 동기화(개념·결정·흐름) ③ PR 이력(사실 위주 짧은 기록). PR 1건이 세 계층 중 영향 있는 파일만 만진다.

규칙 중 가장 고민한 건 컨펌 범위다. 전부 자동 저장하면 틀린 게 조용히 쌓이고, 전부 컨펌 받으면 아무도 안 쓴다. 그래서 LLM이 기존 노트와 비교해 **충돌·확장·순서 변경·단순 관련** 네 가지로 분류하고, 충돌과 미확정만 묻게 했다. 카테고리를 미리 설계하지 않고 작업이 들어올 때 그때그때 만든다는 것도 정했다. 미리 짜 둔 분류는 첫 달 안에 틀어진다.

## 결과와 대가
- 같은 날 엔지니어링 섹션(하위 폴더 8개, 템플릿 5종)과 첫 PR 노트·첫 개념 문서·첫 결정 기록을 한 번에 넣어 패턴을 시연했다.
- 대가: 작성자가 PR마다 질문에 답해야 한다. 응답 시간이 든다.
- 되돌릴 조건으로 "질문 빈도가 부적절하거나 자동 분류 오답이 잦으면 절차 재검토"를 적어 뒀다. 이 일지 저장소를 10월에 만들 때 "위키는 지금 시스템이 어떤가, 일지는 그때 내가 뭘 겪었나"로 축을 나눈 것도 여기서 이어진다.

**요약**: 단체전에서 선수 한 명을 불참 처리하면 라인업 전원이 강제 불참되던 걸, 개별 처리 + "전원 불참 시점에만" 단체 매치 자동 노쇼로 바꿨다.

어드민이 단체전 선수 한 명을 불참으로 바꾸면 같은 팀·체급 라인업 전원이 불참 처리되고 단체 매치가 즉시 노쇼 확정되고 있었다. 실제 운영은 "한 명만 못 나오고 나머지는 정상 출전"이 흔하다. 기존 구현이 운영자의 "1명 불참" 의도를 "팀 전체 이탈"로 왜곡하고 있었던 셈이다.

선택지는 셋이었다. 기존 일괄 변경 유지(부분 불참 표현 불가), 개별 처리 + 라인업 전원 불참 시 자동 단체 노쇼, 운영자가 단체 매치를 따로 노쇼 처리하는 별도 API(동선이 늘고 누락 시 상태가 꼬임). 두 번째로 갔다. 본인만 불참 마킹한 뒤 같은 팀명·체급의 서브매치 참가자 전원이 불참인지 검사하고, 전원이면 단체 노쇼, 누구라도 복귀하면 자동 해제. 조 분리 여부는 무시하고 팀명·체급 단위로 묶는다. 멱등하게 만들어 라인업 전체를 몇 번 호출해도 같은 결과가 나오게 했다.

대가는 호출 한 번으로 끝나던 단순함이다. 트리거 조건 검사가 들어갔다. "일부만 불참이어도 단체를 일괄 노쇼로" 요구가 오면 별도 API를 병행하는 걸로 적어 뒀다.
