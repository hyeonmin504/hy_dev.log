**요약**: 단일 인스턴스 전제로 돌던 Spring Boot 서버를 ECS Fargate 2대 이상에서 돌게 만들고, 오늘 staging 2대에서 끝까지 검증했다. 코드로 푼 건 셋(WS 중계·캐시 무효화 전파·스케줄러 락)이고, 검증에서 "락이 있는데도 순번이 겹치는" 한 건은 멀티 인스턴스 문제가 아니라 REPEATABLE READ 스냅샷 문제로 밝혀졌다.

## 배경과 제약
서버 한 대를 가상머신에서 jar로 띄우던 구조를 9월 초에 컨테이너 블루/그린으로 옮겼다. 그 순간 "인스턴스가 하나"라는 전제가 두 군데서 깨진다. 오토스케일로 2대가 될 때, 그리고 블루/그린 배포가 트래픽을 넘긴 뒤 확정 대기 구간(최대 2시간) 동안 구·신 버전이 같은 DB를 볼 때. 즉 스케일아웃을 안 해도 배포 때마다 이미 멀티 인스턴스였다. 처음엔 이걸 "나중에 스케일할 때 할 일"로 미뤄 두고 있었다.

JVM 안에 있어서 공짜로 공유되던 게 셋 있었다. STOMP 인메모리 브로커, Caffeine 로컬 캐시, `@Scheduled` 타이머. 각각 "공유 저장소로 옮길까, 신호만 전파할까"를 골라야 했다.

## 선택
- **WS 브로커**: 로컬 브로커를 그대로 두고, 보낸 메시지를 Redis pub/sub으로 다른 인스턴스에 중계. Spring의 외부 브로커 릴레이는 RabbitMQ처럼 STOMP를 말하는 브로커만 받아서 Redis로는 못 쓴다. 로컬 먼저 보내는 이유는 Redis가 죽어도 자기 인스턴스에 붙은 클라이언트는 계속 받게 하려고.
- **캐시**: Caffeine을 Redis 캐시로 바꾸지 않았다. 점수판이 몇 초마다 폴링하는 구조라 모든 조회가 네트워크를 타면 손해다. 로컬은 유지하고 "비워라" 신호만 Redis로 보낸다. 30초 만료는 전파가 실패했을 때의 안전망으로 남겼다.
- **스케줄러**: 이건 전파가 아니라 상호배제 문제라 ShedLock. 저장소는 Redis가 아니라 이미 쓰는 DB 테이블. 잡이 몇 초 만에 끝나서 락이 바로 풀리면 다른 인스턴스가 이어서 또 돌기 때문에 최소 보유 시간을 주기 근처로 잡았다.
- **Redis는 단일 노드, 레플리카 없음**. pub/sub 전용이라 보관하는 상태가 없고, 죽으면 로컬 동작으로 저하될 뿐 예외를 내지 않게 했다. 대가는 Redis 재시작 구간에 전파가 끊기고 그때 2대면 잡이 중복될 수 있다는 것.
- **커넥션 풀**: 최소 유휴가 상한과 같은 30이라 유휴 태스크도 30개를 쥐고 있었다. 최대 4대 + 블루/그린 2배면 240으로 RDS 한도(약 340) 턱밑이다. 실측 피크 6.2 req/s에 쿼리 100ms로 잡아도 동시 0.6개라 상주 5로 내리고 상한 30은 적체 여유로 남겼다.
- **공유 저장소 밖의 상태 제거**: 업로드 임시파일은 S3와 DB 참조로, 인증키·시크릿은 시크릿 매니저에서 기동 시 조회, 로그는 stdout. 태스크가 어디 뜨든 같아야 하니까.

## 막혔던 것
- **중계 메시지가 깨져서 도착했다.** 클라이언트에 본문 대신 `{"array":false,"containerNode":true,...}` 같은 게 왔다. 프로젝트는 Jackson 2를 쓰는데 Spring Boot 4의 STOMP 컨버터는 Jackson 3라, 중계로 들어온 Jackson 2 `JsonNode`를 POJO로 보고 게터를 직렬화한 것. 로컬 전송은 원래 DTO라 멀쩡했고, **2대일 때만** 나는 증상이라 1대 운영에선 영영 안 드러났을 버그다. Map/List로 되돌려 넘기게 고쳤다.
- **락 누락**: 락 도입 뒤에 develop에 들어온 SNS 피드 동기화 잡 두 개가 `@SchedulerLock` 없이 합류했다. 2대 띄우고서야 유니크 제약 위반 알림으로 발견. 피드 쪽은 DB가 막아주지만 토큰 갱신은 동시에 두 번 돌면 한쪽이 저장한 토큰이 무효화돼 조용히 죽는다.
- **점수 순번 중복 — 틀렸던 가설.** 점수 저장이 "최대 순번 + 1"을 읽어 쓰는 read-then-write라 경기 행에 `SELECT ... FOR UPDATE`를 걸었고, 커밋 메시지에 "2대면 JVM 단위 직렬화 여지가 사라지니 DB 락이 유일한 방어"라고 썼다. 그런데 오늘 staging 2대에 20건을 동시에 넣으니 순번이 1·2·3 세 값뿐이었다(1×5, 2×8, 3×7). 락이 있는 코드인 걸 확인하고도 한참 "배포된 이미지가 옛 버전인가"를 의심했다. 아니었다. 운영 덤프에도 같은 겹침이 14행 있었고, 그건 1대 시절 데이터다. 멀티 인스턴스 문제가 아니었다.

```pseudo
점수 저장(경기, 점수):                         # 한 트랜잭션, MySQL REPEATABLE READ
  경기 = 조회(경기)                              # 일반 SELECT ← 여기서 읽기 스냅샷이 고정된다
  권한·종류 검증(경기)
  경기 = 조회 FOR UPDATE(경기)                   # 락 읽기. 다른 트랜잭션이 끝날 때까지 대기
  최대순번 = MAX(순번) WHERE 경기                 # 일반 SELECT ← 락 전에 고정된 스냅샷을 본다
                                                 #    방금 커밋된 다른 요청의 행이 안 보인다
  저장(순번 = 최대순번 + 1)
  커밋
```

두 DB 세션으로 그대로 재현했다. 세션1이 일반 읽기로 시작 → 세션2가 한 건 커밋 → 세션1이 FOR UPDATE 잡고 `MAX`를 읽으면 NULL, 같은 `MAX`를 `FOR UPDATE`로 읽으면 1. 직렬화는 되는데 각자 자기가 시작한 시점의 개수를 보고 번호를 매긴 것이다. 고치는 건 max 읽기 두 개를 락 읽기로 바꾸는 것. "JVM 단위 직렬화"는 애초에 없었으니(synchronized 없음) 1대일 때도 같은 확률로 났다.

## 결과와 대가
오늘 staging 2대에서 돈 것들. 요청마다 요청 ID를 붙여 로그 스트림으로 어느 태스크가 처리했는지 추적했다.
- 저장한 태스크와 다른 태스크의 WS 구독자가 210ms 뒤 수신. 캐시 무효화는 양 태스크 반영까지 1.2~2.7초.
- 스케줄러 락은 30분 주기 잡이 태스크를 번갈아 잡았고 256회 중 중복 0.
- 스케일인: 종료 신호 → 10초 뒤 로드밸런서 등록 해제 → 30초 등록 해제 지연 → 그 뒤 앱 graceful shutdown. 1초 간격 GET 254건 전부 200. 끊긴 WS는 등록 해제 +30초에 1006으로 잘렸는데, 앱 종료보다 로드밸런서가 먼저 끊는다.
- 끊긴 뒤 화면이 알아서 돌아오는지는 사람 눈이 필요해서 Playwright로 관리자 화면 2개를 띄워 놓고 봤다. 끊김에서 "연결됨" 복귀까지 2.5초, 새 WS를 남은 태스크에 붙이고 상세·요약을 재조회했다. 그 뒤 넣은 점수 2건이 두 화면 모두에 맞게 떴다.
- 대가: 캐시 stale 창이 0에서 1~3초로(Redis 장애 시 30초). 스케일아웃 직후 새 태스크는 90초 동안 응답 2~20초(로드밸런서 slow start 없음). 장애 분석이 "로그 1개"에서 "요청 ID로 태스크 찾기"로 한 단계 늘었다.

## 남은 것
- SockJS가 XHR 폴링으로 떨어지면 요청마다 다른 태스크로 가서 세션이 깨진다. 로드밸런서 스티키니스가 꺼져 있고 아직 안 켰다. 검증도 WS 업그레이드 경로만 했다.
- 새 태스크 콜드 스타트. slow start나 워밍업.
- 블루/그린 두 버전이 같은 DB를 보는 구간은 expand-and-contract 규칙만 있고 실제 마이그레이션 배포는 아직 안 지나갔다.
- 순번 중복 수정, 그리고 `(경기, 순번)` 유니크 제약은 기존 겹침 14행을 정리한 뒤에.
- 다음에 "락이 있는데 겹친다"를 보면 격리 수준과 스냅샷 고정 시점부터 본다. 락이 걸렸다는 사실이 아니라 **락 뒤의 읽기가 뭘 보는지**가 문제였다.
