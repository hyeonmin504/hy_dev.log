# 0001. 외부 기관 데이터 연동, 수작업에서 무인 자동화까지

날짜: 2026-09-29 (변천은 2026-03 ~ 2026-09)
상태: 채택됨
출처: log/2026/2026-09-29.md

## 요약
외부 기관의 선수·지도자·팀 데이터를 사내 DB로 가져오는 일은 처음엔 사람이 매일 세 단계를 손으로 했다. 동기화 실행과 보고를 Claude 스킬에 맡기는 중간 단계를 거쳐, 지금은 Windows PC 한 대 안에서 수신부터 보고까지 스케줄러가 돈다. 세 단계를 거치며 "어디까지 기계에 맡길 수 있나"의 경계가 두 번 옮겨졌다.

## 변천

| 단계 | 시기 | 사람이 하는 일 | 기계가 하는 일 | 한계 |
|---|---|---|---|---|
| 0. 서비스 탄생 | 2026-03 | 전부 | 외부 DB → 사내 DB 변경 감지 동기화 로직 | 실행은 전부 수동, 운영 절차 없음 |
| 1. 수동 3단계 | 2026-06-11 ~ | ① Windows에서 외부 기관 수신 프로그램 조작 ② 동기화 서비스 띄우고 API 호출 ③ 슬랙 리마인더 스레드에 결과 + 체크 | 동기화 자체만 | 매일 10분 손이 묶임, 빠뜨리기 쉬움, 보고 형식이 들쭉날쭉 |
| 2. 반자동 | 2026-09 초 ~ 09-28 (약 한 달) | ① 수신 프로그램 조작 | ② 동기화 실행 ③ 슬랙 보고 (Claude 스킬) | 보고가 본인 이름이 아님, Claude 로그인에 묶임, 수신은 여전히 사람 |
| 3. 무인 | 2026-09-29 ~ | 노트북을 켜 두고 사내망에 둠 | 수신 → 동기화 → 보고 전부 (작업 스케줄러 + 화면 자동화) | 매 회차 데이터 공백 3분 30초, 매시간 창이 뜸 |

1단계 안에서도 작은 변화가 있었다.
- 처음엔 외부 기관이 매월 1일·15일에만 데이터를 보내서 그때만 돌렸다. 대회 접수 기간엔 하루 두세 번 돌렸다.
- 운영 DB가 클라우드 VM일 때는 동기화 전에 DB 공개 모드를 켜고 끝나면 끄는 단계가 하나 더 있었다. 2026-09 RDS 전환으로 사라졌다.
- 보고는 처음에 변경된 선수 목록을 통째로 붙였다. 2026-07-10부터 "총/생성/수정/스킵/제외/실패" 한 줄로 수렴했고, 이 형식이 3단계까지 그대로 간다. 형식이 먼저 고정됐기 때문에 자동화가 사람 보고와 구분되지 않게 들어갈 수 있었다.

2단계 → 3단계로 넘어가게 한 건 "수신 프로그램 조작"이었다. 동기화와 보고는 코드로 할 수 있는 일이라 먼저 자동화됐고, 소스 없는 GUI 프로그램만 사람 손에 남았다. 이 마지막 조각을 떼어내는 게 3단계의 전부다.

## 3단계의 제약
- 수신 프로그램은 외부 기관이 PowerBuilder로 만든 것이라 소스도 명령줄 옵션도 없다. 화면을 눌러야만 동작한다.
- 수신 서버와 두 DB는 사내망에서만 열린다.
- 실행 PC는 밖으로 들고 나가는 노트북이다. 서버가 아니다.
- 슬랙 보고는 2단계의 교훈대로 본인 이름으로, 리마인더 스레드에 답글로 달려야 한다.

## 3단계 선택지

| 축 | 선택지 | 결과 | 이유 |
|---|---|---|---|
| 수신 프로그램 구동 | 프로그램 수정 / API 요청 | 탈락 | 소스 없음, 공급사 수정 불가 |
| | 화면 자동 조작 | **채택** | 사람 조작을 그대로 재현. 컨트롤은 화면 고유 ID, 창 문구는 Win32로 직접 읽기 |
| 실행 일정 | 클라우드 루틴 | 탈락 | 사내망과 PC 화면이 필요 |
| | BIOS 예약 부팅 + 자동 로그인 | 탈락 | 설정 부담, 자동 로그인은 보안 문제 |
| | Windows 작업 스케줄러 | **채택** | 로그온 상태에서만, 놓친 회차는 다음 로그인 때 1회만 몰아서 |
| 비공개 레포 인증 | 배포 키 | 탈락 | 레포 관리자 권한 필요 |
| | GitHub CLI 로그인 유지 | **채택** | 한 번 로그인하면 유지 |
| 슬랙 보고 | Incoming Webhook | 탈락 | 스레드 답글 불가 |
| | 봇 토큰 | 탈락 | 본인 이름으로 안 올라감 |
| | Claude 연결만 (2단계 방식) | 탈락 | Claude 로그인에 묶임 |
| | User 토큰 + 실패 시 Claude 연결 | **채택** | 본인 이름 유지, 2단계 경로를 대체 수단으로 보존 |
| 빈도 | 1회/일 → 2회/일 | 거침 | |
| | 평일 09~18시 매시 (10회) | **채택** | 데이터 신선도 우선 |

## 결정
작업 스케줄러가 매시 스크립트를 띄우고, 스크립트는 두 DB에 실제 접속되는지로 사내망을 판별한 뒤에만 수신 프로그램을 조작한다. 되돌릴 수 없는 동작(기존 데이터 삭제 후 재수신)은 확인창 문구가 기대값과 일치할 때만 누른다. 이 가드가 테스트 중 실제로 한 번 잘못된 실행을 막았다. 비밀 정보는 Windows DPAPI로 이 PC·이 계정에서만 풀리게 저장한다.

## 결과
- 좋아지는 것: 사람 손 없이 평일 10회 실행, 결과가 슬랙 스레드에 본인 이름으로 보고됨. 노트북이 밖에 있으면 조용히 건너뜀. 1단계 기준 하루 1회 10분이 하루 10회 0분으로.
- 감수하는 것: 매 회차 3분 30초 데이터 공백, 매시간 양쪽 서버 부하, 매시 정각 창이 떠서 작업 방해, 스레드 답글 하루 최대 10개, 노트북을 켜 두고 사내망에 둬야 함.
- 되돌리는 조건: 수신 프로그램에 명령줄이나 API가 생기면 화면 자동화를 버린다. 사내망 제약이 풀리면 서버로 옮기고 스케줄러 대신 클라우드 루틴으로 바꾼다. 둘 다 생기면 2단계 구조(코드만으로 처리)로 돌아가는 게 맞다.

## 돌아보면
- 자동화는 "코드로 할 수 있는 일"부터 떨어져 나갔고, GUI 조작이 마지막까지 남았다. 다음에 비슷한 일이 오면 처음부터 "사람 손에 끝까지 남을 조각이 뭔가"를 먼저 찾는다.
- 보고 형식을 먼저 고정한 게 결과적으로 자동화를 쉽게 했다. 형식이 사람과 기계 사이의 계약이 됐다.
- 2단계에서 "누구 이름으로 보고되나"를 가볍게 봤다가 3단계에서 슬랙 방식을 두 번 바꿨다. 운영 요구는 기술 선택 전에 적어둘 것.
